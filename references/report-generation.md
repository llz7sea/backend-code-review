# 后端代码审查 HTML 评分报告生成规范

本文定义后端审查评分报告的唯一 HTML 产出结构、数据字段、交互同步、安全转义和静态门禁。唯一模板为同目录 ../templates/CODE_REVIEW_REPORT_TEMPLATE.html。

## 问题代码片段展示规则

- 代码审查发现问题时，相关问题代码片段属于审查证据，必须在问题详情中展示，不受“代码展示策略”约束。
- {{codeDisplayPolicy}} 仅控制无问题上下文代码、完整文件内容或大段辅助代码是否展示，不得用于隐藏已判定问题的代码片段。
- 展示问题代码片段前必须脱敏，不得暴露真实密码、Token、密钥、AccessKey、SecretKey、完整内部地址、可访问预览链接、个人隐私等敏感信息。
- 如问题片段无法安全脱敏，应展示最小可复现脱敏片段，并保留文件路径、行号、提交信息、问题说明、影响说明和修复建议。


## 代码审查输出要求

触发代码审查时，`CODE_STYLE.md` 作为编码质量规则来源之一，本文作为审查要求、评分算法、统计口径和输出格式的统一依据；未触发代码审查时，不自动进入评分流程。

| 输出项 | 要求                                                                                                                                                                                                                                       |
| --- |------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 审查类型 | 必须明确属于“当前修改代码审查 / 本人提交代码审查 / 全局时间段代码审查 / 当前项目全部提交审查”之一；用户未明确时，先确认审查类型                                                                                                                                                                    |
| 审查范围 | 明确时间、人员、分支、提交、模块、文件、目录、基线等范围 |
| 涉及目录 | 必须在审查概览中使用紧凑文本树展示本次实际涉及的仓库相对目录，使用 `├─`、`└─`、`│` 表达层级；禁止输出逗号分隔、JSON 数组、绝对路径或平铺路径列表；共同父目录必须合并，目录过长或过多时在容器内部滚动，不得撑破布局                                                                                                                                                                                                             |
| 审查依据 | 只展示从基础分开始的中文分数计算说明；不得展示入口规则、全局索引、评分规则、编码规范、问题分类、HTML 模板等知识库文件名；不得展示原始变量名或英文字段名；必须具体说明基础分、问题扣分、人员得分、多人聚合、风险封顶原因和最终风险分                                                                                                                     |
| 报告输出 | 审查结果必须按 `../templates/CODE_REVIEW_REPORT_TEMPLATE.html` 渲染为 HTML 报告文件并写入 `review-output`；每次审查必须新增报告文件，不得覆盖、修改、续写或复用历史报告；如文件重名，必须追加随机码或短 UUID 后生成新文件；不得用 Markdown 审查正文、Markdown 文件、纯文本或控制台展开内容替代；控制台只输出报告文件位置、文件名或生成状态，不展开得分、问题清单和代码片段 |
| 最终风险分 | 100 分制，报告概览只展示一个最终风险分，不同时展示总分、整体分数、团队综合得分、累计扣分归零分或简单平均分等多个分数字段；该分值必须取评分算法计算后的最终风险分；多人审查必须取多人聚合后的最终风险分，禁止使用累计扣分归零分                                                                                                                        |
| 问题数量 | 报告概览必须展示问题数量，并与问题清单、问题详情、问题跟踪统计保持一致                                                                                                                                                                                                      |
| 提交日志 | 必须展示提交范围摘要和代码位置；按人员统计时必须包含代码变更统计、代码总量占比、AI 编码率；代码变更统计单元格第一行展示 `+新增行数 / -删除行数`，第二行展示 `有效文件 N 个`                                                                                                                                           |
| 问题清单 | 每个问题包含源码位置、人员信息、提交信息、严重等级、规则来源、影响、扣分、建议                                                                                                                                                                                                  |
| 问题代码 | 审查发现问题时，问题详情必须展示对应脱敏代码片段；该要求不受“代码展示策略”约束                                                                                                                                                                                                 |
| 问题跟踪 | 按人员、模块 / 目录、问题级别统计；按人员统计不得展示 AI 编码率和人工编码率                                                                                                                                                                                                |
| 阻断项 | 明确是否存在安全高危、数据破坏、鉴权绕过、资损、不可恢复故障等一票阻断问题                                                                                                                                                                                                    |
| 审查人 | 生成报告前必须获取审查人：必须执行 `git config user.name`获取，非空则作为 `{{reviewer}}`；不得臆造审查人或者使用codex、claude等作为审查人                                                                                                                                            |
| 后续动作 | 给出必须修复项、建议优化项、复审要求、接受风险项                                                                                                                                                                                                                 |


## 唯一模板规则

代码审查 HTML 报告固定使用统一模板：

- `../templates/CODE_REVIEW_REPORT_TEMPLATE.html`

模板使用规则：

1. 标题必须展示审查结果，例如“通过 / 需修改 / 不通过 / 阻断”。
2. 标题背景色必须按评分区间和高风险状态展示，具体分值、状态、扣分和配色判定以 `scoring-model.md` 为准。
3. 审查概览只允许展示一个“最终风险分”，并必须展示“问题数量”；该分值必须按最终风险分展示，多人聚合时不得使用累计扣分归零分、累计扣分封顶 0 分、简单平均分或未封顶原始分。
4. 提交日志必须包含按人员提交统计，至少展示人员、提交数、代码变更统计、代码总量占比、AI 编码率；代码变更统计必须合并展示为两行：第一行 `+新增行数 / -删除行数`，第二行 `有效文件 N 个`；不得在提交日志中展开提交明细。
5. 问题详情必须展示审查发现问题的脱敏代码片段；代码片段只允许围绕问题上下文截取，不得泄露敏感信息。
6. 问题跟踪的按人员统计只展示人员、提交数、问题数、必须修复、扣分、得分，不展示 AI 编码率和人工编码率。
7. 长文本字段必须自动换行、受限滚动或折叠展示，禁止问题摘要、路径、提交日志、代码片段撑破表格。
8. 审查依据区域必须填写具体分数说明，并且必须从“基础分”开始；按评分积分算法用中文列明基础分、扣分项汇总、多人聚合、风险封顶情况、最终风险分和 AI 编码率特征估算过程，不得展示知识库文件名、原始变量名或英文字段名，也不得只写“依据规范审查”。
9. 控制台不得展开 HTML 报告正文，只允许输出报告文件位置。
10. 报告正文必须是基于 `../templates/CODE_REVIEW_REPORT_TEMPLATE.html` 渲染出的 HTML 文件；不得输出 Markdown 审查报告或使用 Markdown 表格 / 列表作为最终审查报告正文。
11. 每次发起审查都必须新增报告文件；生成前必须检查目标文件是否已存在，若存在则在基础文件名后追加随机码或短 UUID，例如 `code-review-20260720-a1b2c3.html`，不得覆盖或回写已有报告。
12. 审查人字段只允许展示真实人名或 Git 提交名，不得展示 `Codex`、`AI`、模型名、工具名、账号类型或泛化角色名称。
13. HTML 报告必须在隐藏数据块 `<script id="reviewDataJson" type="application/json" hidden>` 中嵌入合法 JSON 对象；整个 JSON 必须严格遵守 13.1 的唯一字段合同，完整包含 `summary`、`persons` 和顶层 `issues`，任何层级不得缺字段、多字段、类型错误、使用占位内容或依赖解析器静默忽略未知字段。
14. 审查概览的“涉及目录”必须渲染为紧凑文本树：根节点使用仓库根目录名，子目录使用 `├─`、`└─`、`│` 表达层级，合并共同父目录，只展示本次实际涉及目录；目录名以 `/` 结尾，默认不展示文件；即使只有一个目录也必须保留根节点与树形层级。禁止填充逗号分隔文本、JSON 数组、绝对路径或逐行平铺的完整路径。路径中的 `<`、`>`、`&` 必须先做 HTML 转义；长路径保持单行并横向滚动，目录过多时纵向滚动，不能换行破坏树形连接线或撑破审查概览布局。

目录树固定示例：

```text
backEnd-cloud/
├─ blade-service/
│  ├─ src/main/java/
│  └─ src/main/resources/
└─ rules/
   └─ templates/
```

### 13.1 隐藏审查数据 JSON 严格合同

`{{reviewDataJson}}` 必须渲染为完整、合法、可被 `JSON.parse` 解析的 JSON 对象，并隐藏在 HTML 模板的 `reviewDataJson` 数据块中。这里定义的是**唯一严格合同**，不是推荐结构：对象字段顺序不影响 JSON 语义，但每一层字段集合必须完全一致，不得缺漏、不得多生成、不得重复键，也不得依赖 DTO、序列化器或解析器静默忽略未知字段。

### 13.1.1 顶层固定字段

顶层必须且只能包含以下三个字段：

| 字段 | 类型 | 生成规则 |
| --- | --- | --- |
| `summary` | object | 报告概览、评分、范围、AI 编码率和结论数据，字段合同见 13.1.2 |
| `persons` | array | 按人员汇总的数据，元素合同见 13.1.3；无人员时允许 `[]`，不得写 `null` |
| `issues` | array | 顶层问题事实源，元素合同见 13.1.4；无问题时必须为 `[]` |

固定结构骨架：

```json
{
  "summary": {},
  "persons": [],
  "issues": []
}
```

不得临时增加 `nodeId` 或其他扩展字段。若业务协议确需新增字段，必须先修改本合同，并同步报告生成器、模板校验器、DTO、持久化结构和所有读取方后才能输出；只修改单一环节或依赖未知字段被静默接收均视为门禁失败。

### 13.1.2 `summary` 固定字段

`summary` 必须且只能包含以下字段，所有字段都必须显式生成：

| 字段 | 类型 | 内容要求 |
| --- | --- | --- |
| `codeType` | string | 固定为 `backend` |
| `totalScore` | number | 最终风险分，必须等于可见 `{{score}}` |
| `finalRiskScore` | number | 最终风险分，必须等于 `totalScore` |
| `score` | number | 模板交互同步分，必须等于 `totalScore` |
| `branch` | string | 实际审查分支；确实无法取得时使用已核验的分支或基线说明，不得写通用占位文本 |
| `aiCodingRate` | string | 按规则计算的百分比，格式 `0.00%` |
| `aiCodingMethod` | string | 实际采用的 AI 编码率估算方法 |
| `aiEstimatedLines` | number | 折算 AI 编码量，非负数 |
| `collectedChangedLines` | number | 采集变更代码量，非负整数 |
| `analyzedChangedLines` | number | 实际分析代码量，非负整数 |
| `excludedGeneratedLines` | number | 排除代码量，非负整数 |
| `aiConfidence` | string | 只允许 `高`、`中等`、`低` |
| `aiCodingBasis` | string | 基于真实证据生成的中文 AI 编码率判断依据 |
| `reviewBasis` | string | 与可见报告一致的纯文本中文计分依据，不得包含 HTML、知识库文件名、原始变量名或英文字段名 |
| `reportTitle` | string | 实际报告标题 |
| `reviewScope` | string | 实际审查范围 |
| `reviewTarget` | string | 实际审查对象 |
| `reviewType` | string | 四种审查类型之一 |
| `generatedAt` | string | 实际生成时间，格式必须在生成器内统一 |
| `reviewer` | string | 实际审查人或明确的审查主体 |
| `reviewConclusion` | string | 与当前门禁结果和问题事实一致的中文结论 |
| `reviewResult` | string | 只允许 `通过`、`需修改`、`阻断` |
| `issueCount` | number | 当前确认问题数量，必须等于顶层有效问题数量 |
| `mustFixCount` | number | 顶层有效问题中 `mustFix === true` 的数量 |
| `commitCount` | number | 纳入范围的实际提交数，非负整数 |
| `authorCount` | number | 必须等于 `persons.length` |
| `reviewAuthors` | string | 按人员名称生成；确无人员时固定为 `无` |
| `branchInfo` | string | 可见概览使用的真实分支或基线信息 |
| `commitRange` | string | 真实提交范围 |
| `timeRange` | string | 真实时间范围；审查类型不适用时间范围时写明确的“不适用”说明 |
| `reviewDirectories` | string | 本次实际涉及目录的紧凑文本树，不得写绝对路径或 JSON 数组 |
| `codingRateBasis` | string | 与可见报告一致的 AI 编码率中文判断说明 |

`summary.totalScore`、`summary.finalRiskScore` 和 `summary.score` 必须始终相等。多人场景必须写多人聚合后的最终风险分，禁止写按全部问题累计扣分得到的中间分。所有统计字段必须由当前事实源重新计算，不能沿用删除或改派前的旧值。

### 13.1.3 `persons[]` 固定字段

每个 `persons[]` 元素必须且只能包含以下字段：

| 字段 | 类型 | 内容要求 |
| --- | --- | --- |
| `id` | string | 稳定且非空的人员标识，供顶层问题的 `personId` 关联 |
| `name` | string | Git 作者名、提交人名或已确认人员名，非空 |
| `email` | string | Git 提交邮箱；确实缺失时允许空字符串，不得臆造 |
| `score` | number | 按评分模型从当前顶层有效问题重新计算的个人分 |
| `issueCount` | number | 必须等于本人员 `issues.length` |
| `issues` | array | 人员问题快照，元素合同见 13.1.5；无问题时必须为 `[]` |
| `commitCount` | number | 本人员实际提交数，非负整数 |
| `addedLines` | number | 有效新增行数，非负整数 |
| `deletedLines` | number | 有效删除行数，非负整数 |
| `effectiveFileCount` | number | 有效代码文件数，非负整数 |
| `analyzedChangedLines` | number | 实际分析代码量，非负整数 |
| `excludedGeneratedLines` | number | 排除代码量，非负整数 |
| `aiEstimatedLines` | number | 折算 AI 编码量，非负数 |
| `aiCodingRate` | string | 由 `aiEstimatedLines / analyzedChangedLines` 计算，格式 `0.00%`；分母为 0 时固定为 `0.00%` |
| `aiConfidence` | string | 只允许 `高`、`中等`、`低` |
| `aiCodingBasis` | string | 基于本人员真实代码特征生成的中文判断依据 |
| `codeTotalRatio` | string | 本人员实际分析代码量占整体比例，格式 `0.00%` |
| `codeAmount` | string | 固定格式：`+新增行数 / -删除行数\n有效文件 N 个` |

`includedById`、`includedDeduction`、`mustFixCount` 等仅用于模板运行时计算的临时字段不得写入最终隐藏 JSON。人员名称、邮箱、提交数和代码量必须来自实际 Git 证据；只有合同明确允许的情况才能输出空字符串或零值，不能把默认值当作未采集数据的替代品。

### 13.1.4 顶层 `issues[]` 固定字段

顶层 `issues[]` 是问题与评分的唯一事实源。每项必须且只能包含以下字段：

| 字段 | 类型 | 内容要求 |
| --- | --- | --- |
| `id` | string | 稳定问题码，非空且在同一报告内唯一 |
| `severity` | string | 只允许 `blocker`、`critical`、`major`、`minor`、`info` |
| `deduction` | number | 原始扣分，非负数 |
| `confirmed` | boolean | 是否确认；只有 `true` 的问题参与可见报告和评分，不得省略 |
| `personId` | string | 必须精确关联现有 `persons[].id` |
| `commit` | string | 可复核的真实提交标识；工作区问题使用规范中明确的工作区标识，不得写占位文本 |
| `location` | string | 主代码位置，格式为仓库相对路径加行号 |
| `locations` | array | 归一后的全部代码位置字符串；至少包含 `location` 且不得重复 |
| `module` | string | 实际模块或仓库相对目录 |
| `summary` | string | 与可见问题清单一致的非空中文摘要 |
| `impact` | string | 非空中文影响说明 |
| `fixHint` | string | 非空中文修复建议 |
| `recheck` | string | 非空中文复审方式 |
| `code` | string | 非空、最小且已脱敏的问题代码证据 |
| `mustFix` | boolean | 是否必须修复 |
| `scoringDimension` | string | 非空中文评分维度；统一使用该字段名，不得同时或改用 `dimension` |
| `rootCauseKey` | string | 归一化根因键，非空 |
| `mergedFrom` | number | 归一前合并命中数，正整数 |

顶层问题不得重复键或重复 `id`。`confirmed === false` 的待确认问题可以保留为事实记录，但不得进入 `persons[].issues`、问题数量、个人扣分、团队评分和可见问题列表；删除的问题必须从顶层数组物理移除，不能只从可见区域隐藏。

### 13.1.5 `persons[].issues[]` 固定八字段

每项必须且只能包含以下八个字段：

| 字段 | 类型 | 内容要求 |
| --- | --- | --- |
| `id` | string | 对应顶层有效问题的 `id` |
| `level` | string | 只允许中文 `阻断`、`严重`、`主要`、`次要`、`提示` |
| `deduction` | number | 对应顶层问题的原始扣分 |
| `person` | string | 对应人员的 `name` |
| `commit` | string | 对应顶层问题的 `commit` |
| `location` | string | 对应顶层问题的 `location` |
| `mustFix` | boolean | 对应顶层问题的 `mustFix` |
| `summary` | string | 对应顶层问题的 `summary` |

人员问题数组必须由 `confirmed === true` 且 `personId` 匹配的顶层问题实时派生，不得独立维护。`persons[].issueCount === persons[].issues.length`；无问题人员必须显式输出 `"issues": []`，不得省略、写 `null` 或空字符串。

### 13.1.6 完整生成、重算与静态门禁

- 首次生成、首次渲染、编辑、删除、撤销、改派、保存和下载前，必须从顶层 `issues[]` 完整重建 `persons[].issues[]`、个人扣分、个人分、人员问题数、团队聚合分、风险封顶、最终风险分和 `summary` 派生字段。
- 删除问题后，该问题不得继续出现在顶层问题、人员问题快照、问题清单、问题详情或问题跟踪中，其扣分不得残留；撤销删除时恢复同一问题事实并再次全量重算。
- 整个隐藏 JSON 的内容必须与可见 HTML 一致。字段值必须来自实际 Git 证据、问题事实源、评分算法或 AI 编码率计算；不得用 `null`、空字符串、占位文本、默认零、伪造值或旧缓存绕过生成。只有本合同明确允许的空值、空数组或零值才能输出。
- 必须在对象构造完成后按字段白名单重建最终 JSON，再执行深度校验：逐层校验精确字段集合、类型、枚举、唯一性、外键关联、数组元素、评分派生关系和可见报告一致性。任何未知字段都必须报错，禁止静默丢弃。
- JSON 字符串必须完成 JSON 转义和脚本上下文安全转义，至少处理引号、反斜杠、换行、`<`、`>`、`&` 和可能破坏 `</script>` 的内容。
- 隐藏 JSON 不得包含除 Git 提交邮箱外的未脱敏敏感信息；可见报告已经脱敏的内容，隐藏 JSON 必须采用同等或更严格的脱敏口径。
- 以下任一情况均为静态门禁失败，必须禁止生成、保存或下载报告：字段缺失、合同外字段、重复键、类型或枚举错误、非法空值、占位或伪造内容、问题关联失效、人员问题快照不同步、分数未重算、可见报告与隐藏 JSON 不一致、未知字段被静默忽略。

## 报告输出边界

- Markdown 知识库只负责定义审查报告的规则、状态判定、统计口径和配色标准；最终审查报告正文不得用 Markdown 输出。
- HTML 模板负责承载最终报告结构、占位符和渲染样式；生成代码审查报告时必须使用 `../templates/CODE_REVIEW_REPORT_TEMPLATE.html`，不得自定义 Markdown 报告结构替代。
- 生成审查报告时，应先根据本文规则计算状态、分数、标题 class 和审查人，再将结果写入 HTML 模板。
- 审查结果正文不得直接展开到控制台；控制台只允许输出审查报告文件位置、文件名或生成成功状态，不得输出问题清单、评分细节、代码片段或完整结论。
- 审查报告文件采用只新增不覆盖策略：每次审查都生成新的 HTML 文件；如果目标文件名已存在，必须追加随机码或短 UUID 后写入新文件；禁止因为发现已有报告而修改、覆盖、续写、删除或复用旧报告。
- HTML 报告必须保证问题摘要、代码位置、提交日志等长文本不会撑破表格；长文本必须自动换行、受限滚动或使用折叠块展示。
- HTML 报告必须按统一模板结构输出：标题展示审查结果；审查概览只展示一个“最终风险分”并展示“问题数量”；提交日志必须按人员展示代码变更统计、代码总量占比和 AI 编码率，其中代码变更统计必须合并为 `+新增行数 / -删除行数` 与 `有效文件 N 个` 两行，且不得展开提交明细；第五项“问题跟踪”的按人员统计不得展示 AI 编码率和人工编码率。
- 隐藏 JSON 数据必须与可见 HTML 报告保持一致，并完整通过 13.1 的整个 JSON 严格合同；`reviewDataJson.summary.totalScore` 必须等于 `{{score}}`，`summary.reviewBasis` 必须对应 `{{reviewBasis}}` 的纯文本中文审查依据，顶层问题、人员问题快照、人员统计和所有派生分数必须同步。
- 审查发现问题时，问题详情中的脱敏代码片段必须展示；该要求不受代码展示策略约束，`{{codeDisplayPolicy}}` 只用于说明非问题代码或额外上下文的展示策略。

## 交互一致性补充约束

- 模板顶层 `issues` 是当前问题和评分的唯一事实源；每次首次生成、渲染、编辑、删除、撤销、改派、保存和下载前，必须重建并严格校验整个 `reviewDataJson`，再重新派生 `persons[].issues` 八字段快照、人员问题数、人员得分、团队聚合分和最终风险分。
- 删除问题后，已删除问题不得继续出现在问题清单、问题详情、问题跟踪或任一 persons[].issues 中，其扣分不得残留；撤销删除必须恢复同一条问题及其归属和扣分。
- 保存和下载新版 HTML 前必须重新执行完整计算与静态门禁，确保可见最终风险分与 `reviewDataJson.summary.totalScore`、人员问题数组、问题数量、状态类和门禁结论一致。
- 模板必须离线可打开，不得加载远程脚本、字体、样式或图片；所有动态文本、代码片段、提交信息、路径和作者信息都必须先 HTML/JSON/脚本上下文转义。
