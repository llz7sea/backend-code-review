# 后端代码审查评分模型

本文定义后端代码审查的计分、问题级别、重点审查、多人聚合、风险封顶和状态判定。问题识别与根因去重必须先读取 [issue-catalog.md](issue-catalog.md)；报告字段和模板门禁见 [report-generation.md](report-generation.md)，AI 编码率见 [ai-coding-rate.md](ai-coding-rate.md)。

## 评分总则

| 项目 | 规则 |
| --- | --- |
| 满分 | 100 分 |
| 计分方式 | 从 100 分开始，发现问题后按问题级别、影响范围、证据强度和修复成本扣分 |
| 最低分 | 0 分，不出现负分 |
| 多问题累计 | 多个问题累计扣分；同一根因可合并计分，避免重复惩罚 |
| 证据要求 | 每个扣分项必须能追溯到人员、提交日志、源码位置、问题级别和规则来源 |
| 必算指标 | 触发代码审查时，AI 编码率、新增行数、删除行数、有效文件数、代码总量占比必须实际计算并写入报告，不得空置、跳过或仅写“未统计”；展示时新增行数、删除行数、有效文件数必须合并在“代码变更统计”单元格中 |
| 最终展示分 | 报告概览中的唯一分值必须使用评分算法计算后的最终风险分；可见报告必须写“最终风险分”，隐藏 JSON 的总分必须与该分值一致，不得用累计扣分归零分、未经过风险封顶的原始扣分总分或简单平均分替代 |
| 阻断优先 | 出现一票阻断项时，即使分数未低于阈值，也必须标记为阻断 |
| 不确定问题 | 证据不足时不得直接扣分，应标记为“待确认”并说明需要补充的证据 |
| 代码格式 | 纯格式性问题原则上不参与扣分，除非影响可读性、维护性或一致性 |
| 平均分定位 | 平均分只作为参考指标，不得单独作为团队整体通过依据 |


## 问题级别与扣分准则

问题级别必须使用中文展示，不得在报告中使用英文级别作为主展示；任何内部枚举、数据库枚举或中间态如果使用英文，输出前必须统一映射为中文。

| 级别 | 单个问题扣分 | 必须修复 | 说明 |
| --- | ---: | --- | --- |
| 阻断 | 20-30 | 是 | 导致系统不可用、数据损坏、重大安全风险、合规阻断、无法上线 |
| 严重 | 10-19 | 是 | 高概率线上故障、严重性能问题、权限绕过、核心业务错误 |
| 主要 | 5-9 | 视情况 | 明确影响功能正确性、维护性、扩展性或可测试性 |
| 次要 | 1-4 | 否 | 局部可读性、边界处理、轻量规范问题 |
| 提示 | 0 | 否 | 不扣分的建议、风格提示、可选优化 |



### 6.1 公开扣分口径

- 按问题影响范围、发生概率、修复成本、是否已有测试覆盖、是否影响线上数据综合判断。
- 同一问题同时命中多个类别时，按最高级别扣分，不重复叠加。
- 同一根因在多个文件出现，可合并为一个问题并按影响范围上浮扣分。
- 具体去重合并规则（rootCauseKey / locationFingerprint / descriptionNorm）见 `issue-catalog.md` 第四节，AI 必须按该规则执行以保证扫描幂等。
- 审查发现的问题代码片段必须展示，展示前必须脱敏。


### 6.2 英文级别到中文级别映射

| 英文枚举 | 中文展示 |
| --- | --- |
| Blocker | 阻断 |
| Critical | 严重 |
| Major | 主要 |
| Minor | 次要 |
| Info | 提示 |

### 6.3 级别展示要求

- 报告、模板、统计表、问题清单、问题详情与问题跟踪中，级别列都必须显示中文。
- 如果上游数据已经产生英文级别，必须在渲染前完成映射，不得直接透出。


## 重点审查规则

### 7.1 正确性

- 业务条件判断错误、状态流转错误、事务边界错误、并发控制缺失、幂等性缺失，应按主要到阻断扣分。
- NPE、数组越界、类型转换异常、时间边界错误、金额精度错误，应按影响范围扣分。

### 7.2 安全与漏洞

| 问题 | 建议级别 |
| --- | --- |
| SQL 注入、命令注入、表达式注入 | 阻断 / 严重 |
| 权限绕过、非租户类越权访问、非租户类数据归属校验缺失 | 阻断 / 严重 |
| 明文密码、Token、密钥、AccessKey、SecretKey 泄露 | 阻断 / 严重 |
| 不安全反序列化、任意文件上传 / 下载、路径穿越 | 阻断 / 严重 |
| 敏感日志输出、错误信息暴露内部结构 | 严重 / 主要 |
| 缺失输入校验、输出编码、CSRF / XSS 防护 | 严重 / 主要 |

### 7.3 代码冗余

| 问题 | 建议级别 |
| --- | --- |
| 大段复制粘贴导致业务逻辑分叉 | 主要 |
| 无用方法、无用依赖、无用配置、死代码 | 次要 / 主要 |
| 重复查询、重复远程调用、重复对象转换 | 主要 |
| 可抽象但过度分散导致维护成本明显增加 | 次要 / 主要 |

### 7.4 代码漏洞与健壮性

- 缺少异常兜底、失败回滚、超时控制、重试边界、限流保护，按主要到严重扣分。
- 缓存穿透 / 击穿 / 雪崩风险、并发更新覆盖、分布式锁误用，按严重程度扣分。
- 接口参数未校验、分页缺失、批量操作无上限，按主要到严重扣分。

### 7.5 代码安全审查细则

代码安全审查用于发现越权、注入、敏感信息泄露、身份伪造、数据泄露、文件风险、反序列化风险等问题。AI 日常编码时必须按本章做安全自查；只有用户明确触发代码审查或评分时，才进入评分流程。

#### 1. 身份、权限与数据边界

- 当前用户、组织、角色、权限、部门等非租户类身份信息必须来自服务端可信上下文或可信数据源，不得信任前端传入字段作为当前身份依据；租户字段、租户上下文和租户数据边界按业务规则处理，不作为安全审查问题。
- 涉及查询、修改、删除、导出、审批、批量处理时，只对有明确证据证明外部可控、绕过项目统一鉴权的非租户类资源归属和操作权限问题扣分；租户 ID、人员 ID、发起人等业务参数的传入、透传或参与审批 / 授权 / 跨租户判断，默认不作为安全问题扣分，确需提醒时仅按提示处理。
- 后台管理、定时任务、批处理、跨组织操作必须明确权限边界、数据边界和审计记录。
- 审查时发现越权读取、越权修改、越权删除、越权导出，应按高风险安全问题处理。

#### 2. 输入校验与注入风险

- 所有外部输入必须进行合法性校验，包括请求参数、Header、Cookie、文件名、路径、排序字段、回调地址、表达式、脚本片段等。
- SQL 条件、排序字段、表名、列名不得直接拼接外部输入；确需动态字段时必须使用白名单映射。
- 禁止将外部输入直接传入命令执行、脚本引擎、表达式引擎、模板引擎、反射调用、反序列化入口。
- 审查时发现 SQL 注入、命令注入、表达式注入、模板注入、LDAP 注入、日志注入等风险，应明确标记风险来源和可利用路径。

#### 3. 敏感信息与日志脱敏

- 密码、密钥、Token、证书、验证码、身份证、手机号、银行卡、地址、邮箱等敏感信息不得明文写入代码、配置、日志、异常、测试数据和文档。
- 日志输出对象时不得直接打印完整请求体、完整用户对象、完整认证上下文或完整第三方响应。
- 错误信息不得向前端暴露堆栈、SQL、内部路径、服务地址、密钥名称和值、鉴权细节。
- 审查时发现敏感信息泄露，应记录泄露位置、泄露类型、影响范围和是否需要密钥轮换。

#### 4. 文件、路径与资源访问

- 文件上传必须校验文件类型、扩展名、MIME、大小、数量、存储路径、访问权限和病毒/恶意内容风险。
- 文件下载、预览、删除必须校验资源归属，禁止通过路径参数直接访问服务器任意文件。
- 路径处理必须防止 `../`、绝对路径、软链接、URL 编码绕过等路径穿越风险。
- 审查时发现任意文件读写、路径穿越、未授权下载、上传可执行文件等问题，应按高风险漏洞处理。

#### 5. 加密、随机数与认证凭证

- 密码必须使用安全哈希算法和随机盐，不得使用可逆加密或弱哈希保存。
- Token、验证码、临时凭证、重置链接必须有有效期、使用次数限制和服务端校验。
- 安全随机数必须使用安全随机源，不得使用普通随机数生成认证凭证。
- 传输和存储敏感数据时必须明确加密、脱敏、访问控制和生命周期。

#### 6. 第三方依赖与供应链风险

- 新增依赖必须确认来源、用途、许可证、维护状态和已知漏洞风险，禁止引入无必要依赖。
- 不得使用过期、废弃、存在公开高危漏洞且无缓解措施的依赖版本。
- 不得复制来源不明的代码片段、算法实现、密钥样例或许可证不兼容代码。
- 审查时发现依赖漏洞或供应链风险，应记录依赖坐标、版本、风险说明和升级/替代建议。

#### 7. 安全审查输出要求

安全问题输出必须包含：风险类型、源码位置、可利用入口、影响对象、影响范围、证据、修复建议、是否阻断。

### 7.6 代码冗余审查细则

代码冗余审查用于发现重复实现、无效代码、过度设计、无边界工具类、重复配置、重复 SQL、重复校验、重复远程调用等问题。冗余问题不一定阻断，但会增加维护成本、测试成本和缺陷概率。

#### 1. 重复代码与重复逻辑

- 相同或高度相似的业务规则不得在多个 Controller、Service、Mapper、工具类中重复实现。
- 参数校验、权限校验、状态流转、金额计算、时间范围计算等规则应保持单一来源。
- 重复 SQL、重复查询条件、重复字段映射应抽取到合适层次，避免多个位置各自维护。
- 审查时发现复制粘贴代码，应判断是否存在逻辑漂移、字段遗漏、修复不同步风险。

#### 2. 无效代码与死代码

- 禁止保留未使用字段、未使用方法、未使用变量、不可达分支、空实现、无意义 TODO、注释掉的大段旧代码。
- 临时代码、调试代码、实验代码不得进入主干或交付分支。
- 无调用方的公共方法、无实际效果的参数、永远不会触发的条件分支，应删除或说明兼容原因。
- 审查时发现死代码，应记录是否影响可读性、测试覆盖、后续维护和安全暴露面。

#### 3. 过度封装与过度设计

- 不得为了单一调用场景创建复杂抽象、过多层级、无实际复用价值的接口或工具类。
- 不得用反射、泛型黑魔法、动态代理、复杂设计模式掩盖简单业务逻辑。
- 工具类必须有明确边界，不得形成包含日期、字符串、集合、HTTP、业务规则的“大杂烩工具类”。
- 审查时发现过度设计，应说明其带来的理解成本、调试成本和变更风险。

#### 4. 重复调用与性能冗余

- 循环内不得重复查询数据库、重复调用远程服务、重复读取配置、重复构建昂贵对象。
- 可一次性批量查询、批量校验、批量写入的场景，不得无理由逐条处理。
- 不得重复序列化、重复反序列化、重复转换相同对象或集合。
- 审查时发现性能冗余，应给出触发规模、复杂度变化和替代方案。

#### 5. 冗余审查输出要求

冗余问题输出必须包含：重复位置、重复类型、维护风险、是否已有公共实现、建议抽取层次、是否影响性能或缺陷概率。

### 7.7 代码漏洞审查细则

代码漏洞审查用于识别已经形成可利用路径或高概率缺陷的代码问题，重点关注安全漏洞、稳定性漏洞、数据漏洞、并发漏洞、资源漏洞和业务漏洞。

#### 1. 安全漏洞

- SQL 注入、命令注入、表达式注入、模板注入、路径穿越、任意文件读写、SSRF、XSS、CSRF、反序列化漏洞必须标记为漏洞类问题。
- 身份绕过、权限绕过、验证码绕过、签名绕过、重放攻击、越权访问必须标记为漏洞类问题。
- 明文密钥、默认密码、硬编码凭证、调试后门、未鉴权管理接口必须标记为高风险漏洞。

#### 2. 数据漏洞

- 写操作缺少事务、幂等、唯一约束、状态校验、并发控制，可能导致重复写入、重复扣减、脏数据、串数据时，应标记为数据漏洞。
- 删除、覆盖、导入、同步、批量更新等操作缺少范围限制或确认机制时，应重点审查。
- 非租户类组织 / 用户 / 资源归属边界缺失，且有明确证据证明会绕过授权导致数据越界时，应按漏洞处理；租户查询条件缺失、租户字段缺失或租户上下文差异不作为漏洞处理。

#### 3. 稳定性与资源漏洞

- NPE、数组越界、类型转换错误、除零、时间解析错误、空集合误用等可被输入触发的问题，应按稳定性漏洞记录。
- 连接、流、文件、线程、锁、事务、游标等资源未正确关闭或释放，应按资源漏洞记录。
- 无限循环、无限递归、无界队列、无超时等待、无上限重试、无分页大查询，应按稳定性或性能漏洞记录。

#### 4. 并发漏洞

- 共享可变状态缺少同步控制，可能导致竞态条件、脏读、覆盖写、重复执行时，应标记为并发漏洞。
- 非租户类 `ThreadLocal` 使用后未清理、异步任务丢失非租户类上下文、线程池参数无界、锁顺序不一致，应重点审查；租户上下文未恢复 / 未清理不作为代码审查安全问题。
- 分布式场景下涉及库存、余额、积分、状态流转、任务抢占等逻辑时，必须审查幂等、锁、唯一约束和补偿机制。

#### 5. 业务漏洞

- 状态机缺少前置状态校验、审批流可跳级、金额可被篡改、重复提交可重复生效、接口可被绕过调用，应标记为业务漏洞。
- 仅依赖前端禁用按钮、隐藏字段、页面路由控制来保证业务安全的实现，应按漏洞风险处理。
- 参数边界缺失导致负数金额、超大数量、越界时间、非法状态、非法类型进入核心逻辑时，应按业务漏洞处理。

#### 6. 漏洞审查输出要求

漏洞问题输出必须包含：漏洞类型、触发入口、利用条件、影响范围、源码位置、证据、严重级别、修复建议、验证建议和是否必须修复。

### 7.8 代码审查问题分类

| 分类 | 示例 |
| --- | --- |
| 功能问题 | 需求遗漏、边界错误、兼容性破坏、幂等性缺失 |
| 分层问题 | Controller 写业务、Service 直接拼 SQL、数据访问层写业务判断 |
| 安全问题 | 越权、数据串用、敏感信息泄露、SQL 注入、路径穿越、命令注入、反序列化风险 |
| 数据问题 | 事务缺失、索引风险、分页错误、字段映射错误 |
| 稳定性问题 | NPE、异常吞掉、远程调用未判空、超时重试缺失、资源泄露、并发竞态 |
| 可维护性问题 | 命名差、方法过长、重复代码、死代码、过度设计、魔法值、注释失真 |
| 规范问题 | 统一响应使用错误、DTO/VO 混乱、import/格式不规范 |
| 测试问题 | 无测试、测试范围不足、验证记录缺失 |
| 漏洞问题 | 可利用安全漏洞、数据漏洞、稳定性漏洞、并发漏洞、业务绕过漏洞 |
| 冗余问题 | 重复实现、无效代码、重复 SQL、重复调用、无边界工具类、过度封装 |

## 同人问题递减与个人评分

问题必须先按 [issue-catalog.md](issue-catalog.md) 完成根因归一、位置指纹合并和重复排除，再进入扣分计算。只有 `confirmed !== false` 的已确认问题参与评分；待确认问题不扣分。

### 同人堆叠递减

同一人员的主要和次要问题合并后，按原始扣分从高到低排序，并依次应用递减系数：

| 同人序号 | 递减系数 |
| --- | ---: |
| 第 1 个 | 100% |
| 第 2 个 | 90% |
| 第 3 个 | 80% |
| 第 4 个 | 70% |
| 第 5 个 | 60% |
| 第 6 个及以后 | 50% |

```text
主要/次要问题计入扣分 = 原始扣分 × 对应递减系数
```

- 阻断和严重问题始终按原始扣分全额计入，不参与排序，也不占用递减序号。
- 提示问题固定扣 0 分。
- 递减按人员分别计算，不得把不同人员的问题混合排序。
- 问题清单和问题详情展示原始扣分；问题统计、人员扣分和最终评分使用递减后的计入扣分。
- 同一问题同时命中多个规则时只按最高级别计一次；同根因跨位置问题按码表规则合并后再确定原始扣分。

### 个人评分

```text
人员计入扣分 = 阻断/严重原始扣分之和 + 主要/次要递减后扣分之和
人员得分 = max(0, round(100 - 人员计入扣分))
```

人员统计中的计入扣分可保留两位小数，人员得分按模板统一四舍五入为整数。AI 编码率、代码量和代码占比仅用于统计与解释，不参与人员质量分。

## 多人聚合审查综合评分算法

为避免简单平均分掩盖低分人员，涉及两名及以上人员时必须使用贡献加权、低分尾部和最低人员风险校正；单人审查直接使用该人员得分作为团队原始分。

### 贡献权重与贡献加权分

模板以实际分析代码量的平方根作为人员贡献权重，降低超大提交对团队分的支配：

```text
人员贡献权重 = sqrt(max(0, 实际分析代码量))
贡献加权分 = sum(人员得分 × 人员贡献权重) / sum(人员贡献权重)
```

实际分析代码量必须按 [ai-coding-rate.md](ai-coding-rate.md) 的有效变更口径计算。多人报告中所有人员贡献权重之和不得为 0；若为 0，说明采集口径不完整，必须补齐代码量证据后再生成报告，不得伪造权重或直接发布 0 分报告。

### 低分尾部与最低人员分

```text
低分尾部人数 = max(1, ceil(人员数量 × 20%))
低分尾部得分 = 按人员得分升序取低分尾部人数后的平均分
最低人员分 = 所有人员得分的最小值
```

### 团队原始分

```text
两人及以上：
团队原始分 = round(贡献加权分 × 55%
                 + 低分尾部得分 × 25%
                 + 最低人员分 × 20%)

单人：
团队原始分 = 人员得分
```

简单平均分只能作为参考，不得替代团队原始分或最终风险分。

### 风险封顶与最终风险分

风险封顶按以下优先级判定：

| 条件 | 风险封顶分 | 原因文本要求 |
| --- | ---: | --- |
| 存在任一阻断或严重问题 | 60 | 明确说明存在阻断或严重问题，最终风险分封顶 60 |
| 不存在阻断/严重问题，但任一人员得分低于 60 | 70 | 明确说明存在低于 60 分人员，最终风险分封顶 70 |
| 未触发以上条件 | 100 | 可说明未触发风险封顶 |

```text
最终风险分 = max(0, min(风险封顶分, 团队原始分))
```

- 报告概览中的唯一得分、标题颜色、隐藏 JSON 的 `summary.totalScore`、`summary.finalRiskScore` 和 `summary.score` 必须使用同一个最终风险分。
- 多人审查不得把所有人员的问题扣分汇总后直接从 100 分扣减，也不得用简单平均分替代最终风险分。
- 问题总扣分只用于解释问题来源和人员得分；即使汇总超过 100，也不代表团队最终风险分必然为 0。
- 风险封顶原因必须与实际触发条件一致；低分人员封顶原因不得遗漏。

## 门禁、报告状态与标题样式

### 门禁结论与 body 状态

| 条件 | 门禁结论 | body class |
| --- | --- | --- |
| 存在阻断或严重问题 | 阻断 | `status-high-risk` |
| 无阻断/严重问题，最终风险分低于 60 | 需修改 | `status-fail` |
| 无阻断/严重问题，存在必须修复、主要或次要问题 | 需修改 | `status-change` |
| 不满足以上条件 | 通过 | `status-pass` |

提示问题不单独触发“需修改”。主要或次要问题即使 `mustFix=false`，仍触发“需修改”；阻断或严重问题无论分数多少均优先判定为“阻断”。

### 标题分数区间

高风险状态优先于分数区间：只要门禁为“阻断”，标题必须使用 `score-high-risk`。其余情况按最终风险分选择：

| 最终风险分 / 风险状态 | 标题 class | 含义 |
| --- | --- | --- |
| 阻断或严重高风险 | `score-high-risk` | 深红色，高风险必须修复 |
| 90-100 | `score-excellent` | 绿色，质量较好 |
| 75-89 | `score-good` | 蓝色，可以接受但仍需关注修改项 |
| 60-74 | `score-warning` | 橙色，低分警戒 |
| 0-59 | `score-fail` | 红色，不及格 |

## 审查依据分数说明

`{{reviewBasis}}` 只展示本次审查的中文计算说明，不展示知识库文件名、模板路径、原始变量名或英文字段名。至少包含：

- 基础分 100 分。
- 按阻断、严重、主要、次要、提示统计问题数量、原始扣分、递减后计入扣分和必须修复数量。
- 每个人员的代码变更统计、代码总量占比、AI 编码率、计入扣分和人员得分。
- 多人审查的贡献加权分、最低 20% 人员平均分、最低人员分和 55% / 25% / 20% 聚合结果；单人审查说明直接采用人员得分。
- 是否触发“阻断或严重问题封顶 60”或“人员低于 60 分封顶 70”，以及封顶后的最终风险分。
- AI 编码率的分析代码量、排除代码量、折算 AI 编码量、主要命中特征、置信程度和估算限制，并明确该指标不参与评分和门禁。

推荐表达：

> 基础分 100；主要和次要问题按同一人员内原始扣分降序应用 100%、90%、80%、70%、60%、50% 递减系数，阻断和严重问题全额计入。多人团队原始分按贡献加权分 55%、最低 20% 人员平均分 25%、最低人员分 20% 计算；本次未触发风险封顶，最终风险分为 86。AI 编码率仅作为辅助统计，不参与质量扣分和门禁。

## 评分一致性门禁

生成和每次编辑、删除、撤销、改派、保存报告前，都必须重新执行完整计算并验证：

1. 顶层已确认问题是评分事实源，人员问题数组只能由顶层问题派生。
2. 每个 `persons[].issueCount === persons[].issues.length`，无问题人员为 `issues: []`。
3. 删除问题后，其原始扣分和计入扣分均不再参与人员分与最终风险分；撤销后恢复。
4. `{{score}}`、可见“最终风险分”、标题 class、body 状态和隐藏 JSON 总分完全一致。
5. AI 编码率不进入任何扣分、风险封顶或门禁判断。
